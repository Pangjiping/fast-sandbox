# Review Notes

本文件记录代码评审中发现的问题；通常每个复选项只记录一个问题，但必须写清现状、风险、建议方案和验收重点，修复完成后勾选。Handler Binding/Lifecycle Hook 协议是一次明确批准的例外，以多段形式集中保存完整且相互依赖的协议约束。

- [x] **将 `sandbox-action-fixture` 从 Fastlet 生产镜像中拆出。** 现状：它只是 E2E 使用的假 Handler，负责监听测试端口、响应 `SetBinding`、Lifecycle Hook 和 `RemoveBinding` 并记录调用，但目前被 Fastlet 的构建目标编译并复制进生产镜像，E2E 再用同一镜像覆盖 command 启动它；风险：测试代码污染生产制品，增加镜像体积和攻击面，也使 fixture 改动触发 Fastlet 镜像重建；方案：为 fixture 建立独立的测试镜像或 Docker build target，E2E sidecar 改用该镜像，Fastlet 镜像只保留运行 Fastlet 所必需的二进制；验收：Fastlet 镜像中不存在 `sandbox-action-fixture`，E2E 仍能验证 Binding 配置同步、Hook 订阅与调用顺序、输入传递、Ready Barrier、删除超时以及 Handler 重启恢复。
- [x] **删除 Fastlet 镜像中无人使用的内置 `execd` 副本。** 现状：`build/Dockerfile.fastlet` 通过独立 stage 获取 `execd`，再复制到 Fastlet 根文件系统，但当前设计已经由 `SandboxPool.spec.infraComponents` 声明 execd 的 OCI artifact、digest、注入路径和启动方式，运行时也不会使用镜像内这个本地路径；风险：形成两套交付来源，可能出现版本或 digest 漂移，同时增加镜像体积并误导维护者认为 Fastlet 对 execd 有内置依赖；方案：删除相关 build arg、stage 和 COPY，execd 只按 Pool 的 InfraComponent 配置拉取和注入；如果以后需要预热，应另行设计与 artifact digest、`InfraRevision` 对齐的缓存机制，而不是放置一个游离二进制；验收：声明 execd 的 Pool 仍可正确拉取、注入和启动，未声明 execd 的 Pool 不携带也不启动它。
- [x] **把 Action Binding 的 `input` 改为平台不解释的 opaque string。** 现状：CRD/FastPath 当前使用 JSON 类型或 `input_json` bytes，Fastlet 内部仍以 `ActionBindingInput.InputJSON []byte`、`DesiredInput.JSON []byte` 传递，Handler HTTP 协议的 `action.Request.Input` 也被定义为 `json.RawMessage`，平台因此执行 JSON 校验、RFC 8785 canonicalization、空值归一化和 canonical digest，第三方库对 scalar/null 的限制还引入了数组包装再拆包的实现；风险：即使只把外部 API 改成 string，任一内部层继续保留 `json.RawMessage`/`InputJSON` 都会重新引入 JSON 约束或改写内容，平台也会越权规定业务协议，无法自然承载 YAML、DSL、base64 或普通标识符；方案：CRD 使用 `Input string`，FastPath 使用 `string input`，Fastlet 内部链路统一使用 `Input string`，Handler 请求的业务值也必须是 string，不允许再通过 `json.RawMessage` 直接嵌入任意 JSON；Handler 的 `SetBinding` wire struct 使用 `Input *string` 或等价 presence 表达，其中非 nil 表示创建或更新 Binding、值允许为 `""`，nil 表示 Sandbox 仍存活但该 Binding 已从 Spec 移除；终态 `RemoveBinding` 不读取 input。这样 JSON `{"input":"null"}` 是业务字符串，而 `{"input":null}` 才是解除绑定；平台只验证 Handler 引用、名称唯一性、数量和字节上限，并按原始 UTF-8 字节计算 SHA-256，禁止 JSON 校验、格式归一化和内容改写，二进制由业务方与 Handler 自行约定 base64 等编码；验收：从 FastPath/CRD 经 Controller、Fastlet Manager 到 Handler HTTP body 的字符串与调用方提交内容逐字节一致，wire JSON 中普通值表现为 `"input":"..."` 而非嵌入 JSON，空白或 JSON key 顺序不同会产生不同 digest，`"null"`、`null` 和 `""` 三种输入有独立测试，删除 `internal/actioninput` canonicalizer 及所有 `InputJSON`/`json.RawMessage` Action input 字段，并同步 CRD、proto、生成代码、SDK、文档、单测和 E2E。

- [x] **将 Handler 协议明确拆成 Binding 配置同步与 Lifecycle Hook 两个正交模型。** 当前 `CREATE/UPDATE/DELETE` 同时试图表达“用户修改了 Sandbox desired input”和“Sandbox 到达某个本地生命周期检查点”，导致首次调用、input 更新、Handler 重启重放以及删除清理之间不断互相借用语义。以下是本次 Review 已确认的完整约束；字段最终是否继续使用 `ActionHandler/ActionBinding` 命名可以单独决定，但不得再次合并两类协议。

  **Binding 配置同步：**

  - Sandbox Spec 继续使用有序 Binding 数组，每项包含 Handler 名称和 opaque string input；数组顺序是跨 Handler 的依赖顺序。
  - Fastlet 接受并预占 Sandbox 后，应尽早向每个当前 Binding 发送幂等 `SetBinding(input)`，而不是等待 Runtime Ready 后再猜测这是 Handler 的 CREATE 还是 UPDATE。用户 Update Sandbox input 时也只发送新 generation 的 `SetBinding(input)`。
  - `SetBinding` 成功表示 Handler 已保存最新 input，并已经针对该 Sandbox 当前已到达的生命周期状态完成收敛；否则一个已经 DataPlane Ready 的 Sandbox 更新 egress input 时可能只保存值却不更新现有策略。
  - 用户从仍然存活的 Sandbox Spec 中移除某个 Binding 时发送 `SetBinding(null)`。它是新 desired state 的 Ready Barrier，失败时保留 removing observation 并持续重试；它不是 Sandbox 删除语义。
  - 整个 Sandbox 删除时调用终态 `RemoveBinding`，表示 Handler 应清除该 Sandbox 的全部残留状态；它不携带 input，也不能与 `SetBinding(null)` 混用。若后续认为名称仍易歧义，可以仅做符号级改名为 `DeleteSandbox`/`FinalizeSandbox`，但终态语义不能改变。

  **Lifecycle Hook 订阅与调用：**

  - Handler 定义在 SandboxPool Spec，并增加 `hooks []LifecycleHook`；Pool 是“这个 Fastlet Pod 中的 Handler 订阅哪些 Hook”的权威配置。Sandbox 只有绑定到该 Handler 时才会收到调用；空 hooks 表示配置型 Handler，只接收 Set/Remove。
  - `LifecycleHook` 使用字符串别名和平台提供的内置常量，不做封闭的 protobuf/CRD enum。Fastlet 必须拒绝或将自身标记为不兼容的未知 Hook，不能静默跳过；新增 Hook 不要求改变 wire 数据结构，但每个内置 Hook 必须单独文档化触发时机、可用 context 和重放规则。
  - 第一版只定义 `sandbox.runtime-ready` 与 `sandbox.data-plane-ready`。前者在当前 `runtime.Driver.EnsureSandbox` 成功后触发，此时 runtime 和私有网络身份已可用；当前 runtime contract 没有独立的 Network Ready 屏障，因此不能虚构一个同时间触发的 `sandbox.network-ready`。后者在 Infra Components 初始化完成且 sandbox-proxy route 发布成功后触发。
  - 第一版不定义 `sandbox.ready`，因为 Hook 自身又参与 Overall Ready 时会形成循环依赖；也不定义 `sandbox.before-delete`，因为终态 RemoveBinding 已经发生在 route/runtime/network 拆除之前，当前没有独立业务语义。
  - Lifecycle Hook 只携带 Hook 名称、Sandbox/runtime identity、Binding generation、单调 lifecycle sequence 以及该检查点可用的平台 context，不重复携带用户 input；Handler 将此前 SetBinding 的最新配置与 Hook context 组合执行。

  **时序、Ready 与恢复：**

  - 同一 Sandbox + Handler 的 SetBinding、Hook 和 RemoveBinding 必须串行，并使用 spec generation、runtime instance identity、Handler instance ID、lifecycle sequence/operation token 拒绝旧结果；不同 Sandbox 仍可并发。
  - `SetBinding` 和所有已到达、已订阅的非终态 Hook 都是 Ready Barrier：失败不阻止 Fastlet继续创建 runtime、初始化 Infra 或发布 route，但 Sandbox Overall Ready 必须保持 False，并由 Fastlet 重试到成功。某 Handler 的 Hook 必须等该 generation 的 SetBinding 成功后才能调用；如果生命周期检查点先到达，则记录 Pending，待 SetBinding 成功后按平台生命周期顺序补发。
  - Handler `instanceId` 变化表示 Handler 进程重启并可能丢失本地状态。Fastlet 必须先重发最新 `SetBinding(input)`，再按顺序重放该 Sandbox 当前已经到达且该 Handler 订阅的 Hook；普通 input Update 只调用 SetBinding，因为 SetBinding 本身承诺针对当前生命周期状态收敛。
  - Binding declaration order继续决定同一 Hook 上多个 Handler 的正向调用顺序；解除 Binding 和 Sandbox 删除使用反向顺序。不得依赖 exactly-once，逻辑调用重试复用稳定 invocation/event identity，Handler 必须幂等。
  - Sandbox 删除先在 Fastlet 本地原子标记 Terminating，阻止新 SetBinding/Hook，再在一个固定的 5 秒总预算内按反向 Binding 顺序调用终态 RemoveBinding；错误或超时写入诊断但不阻塞 route/runtime/network 清理。这个 5 秒是整个 Handler 清理阶段的共享 deadline，不是每个 Handler 各自 5 秒，第一版不暴露 Pool 级可调参数。
  - CRD/FastPath 的 Binding Ready 表示“当前 input 已 SetBinding 且截至当前 Sandbox 生命周期检查点的所有订阅 Hook 均成功”，而不是某一次 HTTP 调用成功；每次 Hook 历史、pending invocation、Handler instance 和重试细节保留在 Fastlet 内部，不扩散成大量公共 Status 字段。

  **验收重点：** 创建时 SetBinding 先于相关 Hook；Handler 只收到 Pool 中订阅的 Hook；空 Hook Handler 仍能完成 Set/Remove；input 更新立即作用于已经运行的 Sandbox；Spec 移除发送 null 而不是终态 Remove；Handler 重启按“SetBinding→已到达 Hook”恢复；Runtime/DataPlane Hook 失败只阻止 Overall Ready；删除并发下不再接收新调用且全部 Handler 清理共享 5 秒；旧 generation/runtime/Handler instance 的迟到响应不能覆盖新状态；多个 Handler 保持正向建立、反向清理顺序，并覆盖 race、超时和 E2E 调用计数。

- [x] **将 FastPath 公共协议中的 `user_metadata` 统一改名为 `metadata`。** 现状：Create/List 使用 `user_metadata`，Update 却使用 `metadata_upsert` 和 `metadata_delete_keys`，公共 API 站在服务端视角称调用方为 user，且同一概念命名不一致；风险：增加 API 理解成本，也容易让调用方误以为它与另一类 `metadata` 并存；方案：Create 和 List 对外统一使用 `metadata`，保留原 protobuf field number 以维持 wire compatibility，Update 继续使用 `metadata_upsert`/`metadata_delete_keys`，仅在内部需要区分平台标签、注解或系统元数据时使用 `userMetadata` 变量名；同时明确该字段只保存用户自定义键值，平台保留前缀不可写；验收：Create/Get/List/Update 的文档和 SDK 使用一致术语，旧 wire 数据仍可解码，并补齐 reserved key 校验及元数据增删改查测试。
- [x] **删除 FastPath `SandboxInfo` 中没有可靠实时来源的冗余状态字段。** 现状：FastPath 的 `SandboxInfo` 是 CRD 身份/期望状态与 Fastlet 实时观测的聚合裁剪视图，但 Runtime/DataPlane 的 `last_transition_unix_seconds` 当前始终为 0，二者的 `message` 只能复用通常为空的 Sandbox 级消息，InfraComponent 的 transition time 在 Fastlet diagnostics 中也没有来源；风险：对外暴露“看似精确、实际不可用”的字段，客户端可能把 Unix epoch 0 当成真实状态或依赖永远为空的诊断信息；方案：FastPath 仅保留 `RuntimeInfo.state`、`DataPlaneInfo.state`、InfraComponent 的 `name/state/message`，Action Binding 因 Fastlet 确实掌握调用结果而保留 `handler/state/last_transition/message`；完整的 transition time、Message、Conditions、Placement、Recovery 和 generation fence 继续由 Controller 维护在 CRD Status 中，因此 CRD 是持久语义超集，FastPath 是面向即时使用的实时视图；验收：FastPath 不再返回无意义的 0 时间戳或伪诊断字段，同时 `ready`、`applied_generation` 和 Action 状态仍能由真实数据构造，proto、生成代码、SDK、文档和测试全部同步。

- [x] **按副作用边界拆分 Fastlet `SandboxManager.CreateSandbox`，使本地 admission 与 runtime 创建流程可直接阅读。** 现状：`internal/fastlet/sandbox/admission.go` 的入口从第 24 行开始同时负责 tracing/metrics、请求校验、Identity 合入 SandboxSpec、profile 校验、锁内 runtime/infra/Handler readiness 检查、已有 Sandbox 幂等处理、tombstone generation fence、draining/capacity/network resource admission、`creating` placeholder 预占、`EnsureSandbox`、失败后的 runtime DELETE 与 cleanup-failed 状态、runtime 返回元数据归并、并发 DELETE 处理、镜像保护、Binding/Infra/route/Hook 后续阶段启动以及 completion 等待；风险：锁的持有与释放分散在大量 return 分支中，任何局部改动都可能造成漏解锁、错误 fallback outcome、重复创建或把“结果未知”误报成“无副作用拒绝”，而 runtime 创建失败、cleanup 失败和创建期间 DELETE 的语义也难以独立测试；方案：保持入口只呈现 `prepareCreateSpec`（校验并把 Identity 合入 spec 的本地副本）、`reserveSandboxForCreate`（在一次锁临界区内完成 readiness、已有实例/cleanup retry、tombstone、draining、容量与资源判断并写入 placeholder）、`registerDesiredBindings`（在 runtime 创建前登记 generation 并尽早启动非阻塞 SetBinding）、`ensureRuntime`、`handleRuntimeCreateFailure`（runtime DELETE 补偿、placeholder 清理或标记 `create-cleanup-failed`、确定 outcome/error code）、`commitRuntimeCreate`（归并 runtime/network 字段并原子处理并发 terminating）、`recordRuntimeReadyAndDispatchHooks`、`continueDataPlaneCreation` 与现有 `finishCreate`；不要把流程包装成泛化的 plan/executor，也不要把原本要求原子的 admission 检查拆成多个锁区间，helper 应返回明确的 reservation/response/error 而不是多个含义不明的 bool；验收：入口能在一个屏幕内看清“准备→预占→登记 Binding/启动 SetBinding→创建 runtime→提交并触发 Runtime Hook→继续数据面/触发 DataPlane Hook→按 completion 返回”，并保留已有请求幂等、generation fence、容量拒绝、资源不足、Ensure 失败且清理成功、清理失败可重试、创建期间并发 DELETE、RUNTIME_READY/READY completion 以及 Binding/Hook Ready Barrier 的测试覆盖，另用 race test 验证重构未破坏锁、placeholder 和 lifecycle checkpoint 语义。
